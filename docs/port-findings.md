# Port findings

Things noticed in the userscript logic while porting it. The port keeps the behaviour as is (logic freeze); fixes wait until parity is signed off.

| # | Where | Finding | Effect | Status |
|---|---|---|---|---|
| 1 | `getStrikeDetails` (utils.js) / `engine/levels.ts` | The step string is split on "," and each part parsed with `parseInt`. A single value (no comma), which `_dlStrikeDiffString` returns when a stock's min and max step are equal, gives strikeTwo = NaN, so AST and BST become NaN and the name can never be classified AST or BST. | Affects only names whose NSE step is a single value. On 2026-11-20 no name in the 226-name universe had this (checked), so it did not change any zone that day. | Kept as is. Test: `scan915.test.ts` "single step value". |
| 2 | `scanNineFifteenCandle` | `INDIA VIX` is in the scanned universe and has no strike step, so it is classified with the 100,100 placeholder. | Meaningless levels for INDIA VIX (the app treats it as a special case elsewhere). The new scan keeps it and flags `stepKnown: false`. | Kept as is. |
| 3 | `scanNineFifteenCandle` | The anchor is `candles[0]`, the first candle returned for the day, not specifically the 09:15 candle (only GIFT NIFTY is anchored to 09:15). | Same for every NSE name (first candle is 09:15). Differs only if Kite returns an earlier candle. | Kept as is. |
| 4 | `showTrendingOI` / `_dlNearestLiveExpiry` | The nearest-live-expiry rule compares expiries with the REAL today (`moment()`), not the trading day shown. On a replay of a past day it therefore picks an expiry that was not the nearest then, unless an expiry is set in Settings. | The backend uses the trading day being loaded as the reference (so a past day resolves to the expiry that was live then). Live days are identical. | Deliberate difference for past days; live behaviour unchanged. |
| 5 | `showTrendingOI` | The strike count override is ignored for the indices: NIFTY 50, NIFTY BANK, NIFTY FIN SERVICE, NIFTY MID SELECT and SENSEX always use 3 strikes each side (the code overwrites the argument). | A caller asking for a different count on an index silently gets 3. | Kept as is. Test: `optionChain.test.ts`. |
| 6 | `calculateIVSeries` | IV is inferred from the option's candle close and the spot close of the same candle with a fixed 6.5% rate, so CE and PE IV can differ a lot at the same strike (seen on 2026-11-20: ATM CE 8.3% vs PE 15.9%). | Display only; the OI/OBV scoring already treats IV as a secondary signal. | Kept as is. |
| 7 | futures REMARK parity | Run on the recorded days 2 to 6 Nov 2026 (1,125 slots): the intraday VWAP matches the saved one on 1,125 slots, the saved SENSEX remark matches on 375 of 375, but the saved NIFTY 50 / NIFTY BANK remarks match only 808 of 1,125. The ORIGINAL userscript function (`_gtbClassifyFutures`, loaded into the oracle sandbox) was run on the same candles: it equals the port on 1,125 of 1,125 slots and equals the saved remark on exactly the same 808. | The port is faithful. The saved NIFTY / BANK remarks in the snapshots were not produced by this function from these candles and the recorded VIX: another code path or a stale value wrote them (several paths write `futures_trend_remark`). Moving the time cut, dropping the open-only candle or changing the VIX scale does not explain it. | RESOLVED for the port (original == port). The cause inside the old app's refresh is not needed to proceed; treat the old NIFTY / BANK stored remarks as unreliable. |
